# Bug 修复 AI 交接与执行手册

## 1. 角色

Bug 修复 AI 是本项目的质量负责人。目标是稳定复现、定位根因、提交最小安全修复并证明没有破坏科研主流程；不是重新设计产品，也不是趁机扩需求。

## 2. 每次开始前的阅读顺序

1. `docs/PRODUCT_CHARTER.md`
2. `docs/ARCHITECTURE_GUARDRAILS.md`
3. `docs/IMPLEMENTATION_STATUS.md`（实现任务创建后维护）
4. `docs/BUGFIX_PLAYBOOK.md`
5. 对应模块 README、测试和最近提交

如果实现与产品宪章冲突，先报告冲突，不擅自把冲突固化为修复。

## 3. 必要输入

一个可开始处理的 Bug 至少需要：

- 当前 commit 或版本号。
- Windows 版本、Node/pnpm/dsh 版本。
- 精确启动/安装命令。
- 最短复现步骤。
- 期望结果与实际结果。
- 完整错误文本或日志文件路径。
- 截图/录屏以及发生时间。
- 是否每次发生、是否只在特定窗口尺寸/主题/模型/插件状态发生。
- 最近一次正常版本或可疑变更。

信息不足时，先做无副作用诊断；不要凭截图直接改 CSS 或凭异常最后一行猜根因。

## 4. 严重级别

- P0：数据/密钥泄露、不可恢复数据损坏、错误扣费、供应链风险。
- P1：应用无法启动、无限 Loading、主流程完全阻断、更新后无法运行。
- P2：主流程可绕过但明显错误、状态丢失、严重遮挡、重复生成。
- P3：轻微视觉、文案、低频边界问题。

P0/P1 优先停止发布并保留证据；P2/P3 正常进入修复队列。

## 5. 标准修复流程

1. **确认基线**：记录 `git status`、commit、版本和相关配置；不清理用户改动。
2. **稳定复现**：使用最小步骤复现，并保存日志、截图、请求或状态快照。
3. **缩小范围**：区分桌面壳、DSH host、browser plugin、业务状态、样式或环境问题。
4. **写失败证明**：优先增加会失败的回归测试；UI 问题至少有同视口前后截图和明确断言。
5. **根因说明**：用一段话解释触发条件、错误机制和影响面。
6. **最小修复**：只改根因所在层；不在同一个补丁里做无关重构。
7. **分层验证**：相关单测/契约测试 → 类型检查 → 构建 → 启动 → 核心路径 → 失败路径。
8. **视觉验证**：使用 Browser 工具检查桌面和窄窗口；把修复前参考与修复后截图并排比较。
9. **交付记录**：更新实现状态、变更日志和 Bug 条目，列出未覆盖风险。

## 6. DSH 常见故障分类

### 卡在 Loading plugins

检查插件 browser half 是否抛异常、模块是否无法解析、`apply` 是否等待异步任务、是否覆盖 single slot、错误边界是否缺失。修复必须保证单个科研插件失败时 Harness 仍能进入原生界面。

### `EADDRINUSE 127.0.0.1:3080`

先确认占用 PID 和是否为已有合法实例；不要直接随机杀进程。桌面壳应实施单实例与端口所有权策略。

### `dsh` 无法识别

区分未安装、终端未刷新 PATH、npm 全局目录不在 PATH 和版本不匹配。不要通过硬编码个人机器路径修复。

### pnpm ignored builds / peer warning

区分警告和真正失败。只批准确实需要且经过审核的依赖脚本，不给所有包开放构建权限。

### 猫咪遮挡

先测量控件、浮层和猫咪热区的实际矩形与层级；修复交互优先级、避让状态和窄窗规则，不只为单张截图写绝对坐标。

### 自动更新失败

验证 manifest、签名/校验、版本比较、下载中断和回滚。不得在修复中绕过验证。

## 7. 最低验收输出

每个修复最终必须给出：

- 根因。
- 修改文件和影响范围。
- 回归测试或复现证据。
- 实际运行过的验证命令及结果。
- UI 前后证据（适用时）。
- 剩余风险与回滚方式。

不能复现时不得宣称“已修复”；应写明诊断结果、排除项和下一项所需证据。
