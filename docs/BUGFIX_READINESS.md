## 3. 当前质量判断基线

发生冲突时，Bug 判断和验收依次服从：

1. 本地论文、笔记、会话上下文、密钥和插件供应链安全。
2. DSH 原生会话、工作区、模型、权限、工具和设置保持可用。
3. 猫猫、论文和插件市场相互隔离；任一模块故障不得拖垮另外两个模块或让 DSH 永久 Loading。
4. 论文内容默认本地保存；只有用户明确选择或授权的内容才能进入 DSH/模型上下文。
5. 插件市场必须复用 DSH 官方插件格式、profile 和管理机制，并提供权限披露、兼容性判断、完整性校验及失败回滚。
6. 猫猫可关闭、遵循减少动态效果，并避让输入、菜单、弹窗、论文阅读器和安装确认等关键操作。
7. 旧的“今日 / 科研绘图 / 猫窝”、FigureBrief、报价、计费和 gpt-image-2 交付闭环不属于当前正确行为，不得据此创建或关闭 Bug。

## 5. 每个 Bug 必须提供的证据

提交 Bug 时使用 `docs/BUG_REPORT_TEMPLATE.md`，至少填写：

1. 当前应用版本或完整 commit，以及复现时工作区是否有未提交改动。
2. Windows、Node、pnpm、dsh、应用和相关插件版本。
3. 实际使用的安装/启动命令；不得包含密钥或其他秘密值。
4. 能稳定触发问题的最短步骤，以及问题发生前所需状态。
5. 期望结果、实际结果、发生频率和首次/最近发生时间。
6. 完整错误文本或安全脱敏后的日志文件路径，并标记关键时间点。
7. 截图或录屏；UI Bug 还需浏览器、视口、缩放、主题、减少动态效果和插件状态。
8. 最近正常版本、可疑变更或已排除项（如已知）。
9. 论文/笔记/会话数据、上下文外发、插件安装状态、密钥或个人信息等安全影响。
10. 可接受的验收标准，以及是否允许在指定浏览器中进行 UI 验证。

证据不得包含 `.env` 内容、令牌、数据库、备份、上传文件或真实用户数据。需要日志时，应先脱敏并只提供与缺陷相关的最小片段或安全路径。

## 6. 修复任务的证据链

每次收到具体 Bug 后，按 `docs/BUGFIX_PLAYBOOK.md` 保存并报告以下证据：

- **基线证据**：commit、分支、工作区状态、环境版本与实际启动命令。
- **失败证据**：修复前可重复失败的测试，或同一视口下的 UI 复现、日志与明确断言。
- **根因证据**：触发条件、错误机制、责任层和影响范围，不以最后一行报错或单张截图代替分析。
- **补丁证据**：只包含根因层的最小改动，并保留现有用户改动。
- **验证证据**：相关测试、类型检查、构建、启动、DSH 原生能力、受影响模块主路径与失败降级路径的实际命令和结果。
- **UI 证据**：适用时使用用户选择的 Browser 能力，在相同视口、缩放、主题和状态下比较修复前后；不得只凭截图猜 CSS。
- **交付证据**：改动文件、剩余风险、未覆盖项和可执行的回滚方式。
